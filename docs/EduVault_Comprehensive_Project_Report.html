1. INTRODUCTION

Higher education institutions generate enormous volumes of academic records, including degree certificates, semester marksheets, co-curricular awards, industrial internship validations, and technical project portfolios. However, the management, storage, verification, and dissemination of these records have historically remained fragmented across manual paper archives, disparate department files, and unverified digital scans. This fragmentation causes severe delays in institutional background checks, fosters academic fraud, burdens placement departments with manual spreadsheet compilation, and isolates graduated alumni from active university mentorship networks.

This chapter describes existing credential management practices and their limitations, introduces the proposed EduVault ecosystem, defines the project scope, outlines hardware and software operational environments, and justifies the technology selections powering the platform.

1.1 EXISTING SYSTEM, PROPOSED SYSTEM AND NEED AND OBJECTIVE OF SYSTEM

1.1.1 Existing System

Academic credential management and campus placement coordination currently depend on four loosely coupled, manual procedures:

(a) Physical Paper Transcripts & Unauthenticated PDF Scans.
Students submit physical photocopies or generic PDF scans of their credentials during semester evaluations and campus placement registrations. These files are not cryptographically tied to an institutional source of truth. Consequently, they are vulnerable to alteration, forged seals, and manipulated marks using basic graphic editing tools.

(b) Manual Administrative Verification Workflows.
Institutions establish academic verification committees to authenticate student credentials. However, verifiers must manually retrieve physical ledger books or query disconnected database spreadsheets. This creates heavy administrative backlogs, with third-party background verification agencies frequently waiting two to four weeks for manual transcript confirmations.

(c) Fragmented Campus Placement Compilation.
Training & Placement Officers (TPO) spend countless hours compiling candidate data (CGPA, active backlogs, departmental affiliations, and project links) through Google Forms or spreadsheets. This self-reported data is prone to human error, lacks instant verification, and cannot be dynamically presented to corporate recruiters.

(d) Static Alumni Communication Silos.
Upon graduation, alumni contact records deteriorate into static contact sheets. Universities lack an interactive, database-backed registry where alumni can advertise current company designations, share locations, and declare availability for student mentorship.

1.1.2 Proposed System

EduVault is an end-to-end, enterprise-grade Digital Locker, Academic Credential Verification, and Career Networking Platform. It unites students, verification committees, placement officers, alumni, and external recruiters within a secure, role-governed web application. The platform operates across six core functional tiers:

  1. Authentication & Role Governance Tier: Issues signed JSON Web Tokens (JWT) using Django REST Framework SimpleJWT, routing users automatically into one of four tailored portals: STUDENT, ALUMNI, COMMITTEE, or PLACEMENT.
  2. Student Digital Vault: Enables students to upload, categorize, and track semester marksheets, degree certificates, and achievement files (≤ 5 MB). Uploaded records initiate in a PENDING state.
  3. Academic Committee Verification Pipeline: Provides faculty reviewers with a real-time review queue, in-app full-screen document previewers, instant verification approvals, or rejection feedback mechanisms.
  4. Cryptographic Interview Key & QR Engine: Generates unique UUID-based cryptographic endpoints (e.g. /student/:id and /verify/:id) that render as high-resolution QR codes, enabling corporate recruiters to scan and inspect verified student credentials on mobile devices instantly.
  5. Placement & Corporate Relations Dashboard: Empowers placement teams with aggregate talent metrics (Total Students, Verified Ratio, Average CGPA), instant text search, and multi-tier CGPA threshold pills (≥ 9.0, ≥ 8.0, ≥ 7.5, ≥ 7.0).
  6. Dynamic Alumni Network: An interactive, database-backed directory allowing graduated alumni to publish current roles, employers, geographic locations, and mentorship availability tags.

1.2 SCOPE OF WORK

1.2.1 Functional Scope

The functional scope encompasses all user-facing interactions across the platform:

  • User Registration & Profiling: Account creation with department, college, PRN, phone, and role assignment.
  • JWT Session Security: Token issuance, automated refresh token rotation via Axios interceptors, and logout handling.
  • Student Vault Management: Uploading, previewing, and deleting unverified academic documents.
  • Institutional Committee Queue: Queue sorting, filtering by status/category, full-screen document inspection, single-click verification, and rejection with feedback.
  • Recruitment & Placement Engine: Live talent metrics, candidate search, CGPA threshold filtering, and verified dossier export.
  • Dynamic Alumni Network: Real-time alumni registry with employer, role, location, and mentorship availability filters.
  • Public QR Verification: Tokenized, unauthenticated read-only candidate dossier view for external corporate recruiters.

1.2.2 Technical Scope

  • Backend REST Service: Python 3.11 with Django 6.0 and Django REST Framework, served via Gunicorn WSGI.
  • Persistence: PostgreSQL 16 (Neon Serverless Cloud) managed through Django ORM with ACID-compliant transactions and foreign key cascades.
  • Frontend Application: React 18 with Vite build engine, React Router DOM v6, Tailwind CSS, Lucide React icons, and QRCode.react.
  • Cloud Infrastructure: Vercel for SPA hosting with edge routing; Render for Python WSGI container execution.

1.2.3 Out of Scope and Boundaries

  1. Dynamic Analysis & OCR: The system stores and displays files; automatic character recognition (OCR) of scanned certificates is excluded from the current release.
  2. Automated Grading: The platform tracks CGPA and marksheets; it does not compute semester examination grades from scratch.
  3. Payment Gateway Integration: Administrative transcript fees are handled externally; online financial transactions are out of scope.
  4. Native Mobile Apps: The system is built as a fully responsive Web App; native compilation for Android APK or iOS IPA is not implemented.

1.4 Description of Technology used

1.4.1 Python 3.11 Runtime Environment

Python 3.11 serves as the core backend programming runtime. It provides superior memory optimization, enhanced error tracebacks, and fast execution speed. Python's rich ecosystem facilitates seamless database communication, file handling, and cryptographic verification.

1.4.2 Django 6.0 and Django REST Framework (DRF)

Django provides a mature, secure web framework featuring built-in defenses against Cross-Site Scripting (XSS), SQL Injection, and Cross-Site Request Forgery (CSRF). DRF provides high-throughput serialization, multipart form parsers for document uploads, and granular permission classes.

1.4.3 SimpleJWT Token Authentication Architecture

Stateless authentication is implemented using JSON Web Tokens (RFC 7519). Upon authentication, the server signs an access token (5-minute expiry) and refresh token (24-hour expiry). The client transmits the access token in HTTP Authorization: Bearer <token> headers.

1.4.4 React 18 and Vite Tooling Engine

React 18 delivers a declarative, component-driven user interface. Reactive state hooks (useState, useEffect, useMemo) ensure sub-second UI updates without page reloads. Vite serves as the modern build engine, utilizing native ES modules for instantaneous development server start and optimized production bundling.

1.4.5 Tailwind CSS and Lucide React Visual Components

Tailwind CSS replaces bloated CSS stylesheets with utility classes, enforcing uniform padding, typography, dark borders, and color coding. Lucide React provides crisp SVG iconography across all system navigation elements.

1.4.6 PostgreSQL 16 and Neon Serverless Persistence

PostgreSQL 16 handles structured data persistence. Neon Serverless PostgreSQL decouples compute from storage, allowing zero-maintenance database hosting with instant scale-to-zero capabilities and strict ACID compliance.

1.4.7 QRCode.react and Cryptographic Token Verification

Dynamic QR codes are generated directly in the client DOM using qrcode.react. Each QR encodes a unique URL resolving to the candidate's public verification endpoint (e.g. https://eduvaul.vercel.app/student/:id), verifiable on any camera-equipped smartphone.

1.4.8 Gunicorn WSGI and WhiteNoise Production Static Server

Gunicorn acts as the production WSGI application server, managing concurrent worker processes. WhiteNoise integrates directly into Django's middleware pipeline, serving compiled static assets directly with brotli/gzip compression and far-future cache headers.

5.4 DEFECTS FOUND AND RESOLVED

5.4.1 Defect 1: Production Media File 404 Resolution (DEBUG=False)

Table 5.3: Defect 1 record.
Field Detail
Defect IDDEF-01
Componentconfig/urls.py, Django Media Routing
SeverityHigh: Uploaded certificates returned "404 Not Found" on the live server.
Detected InCloud deployment verification when clicking "View File" on Vercel/Render.
StatusResolved

Symptom: When students uploaded certificates on the live deployed system, clicking "View File" opened a new tab at https://eduvault-backend1.onrender.com/media/... showing 404 Not Found: The requested resource was not found on this server.

Root Cause: In development, Django serves media using if settings.DEBUG: urlpatterns += static(MEDIA_URL). However, in production on Render, DEBUG = False, causing Django to strip all media routes from the URL configuration.

Resolution: Added explicit media serving using re_path and django.views.static.serve regardless of debug state, and updated frontend links via getMediaUrl():

# config/urls.py
from django.urls import re_path
from django.views.static import serve
from django.conf import settings

# Explicitly serve uploaded media files in development and production
urlpatterns += [
    re_path(r"^media/(?P<path>.*)$", serve, {"document_root": settings.MEDIA_ROOT}),
]

6.2 Document Validation & Model Architecture (documents/models.py)

import uuid
from django.db import models
from django.conf import settings
from django.core.exceptions import ValidationError

def validate_document_file(value):
    max_size = 5 * 1024 * 1024  # 5 MB
    if value.size > max_size:
        raise ValidationError("File size must not exceed 5 MB.")
    allowed_extensions = [".pdf", ".jpg", ".jpeg", ".png"]
    if not any(value.name.lower().endswith(ext) for ext in allowed_extensions):
        raise ValidationError("Only PDF, JPG, JPEG and PNG files are allowed.")

class Document(models.Model):
    user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name="documents")
    verification_id = models.UUIDField(default=uuid.uuid4, unique=True, editable=False)
    title = models.CharField(max_length=200)
    category = models.CharField(max_length=20)
    file = models.FileField(upload_to="documents/", validators=[validate_document_file])
    status = models.CharField(max_length=20, default="PENDING")
    rejection_reason = models.TextField(blank=True, null=True)
    verified_at = models.DateTimeField(blank=True, null=True)
    created_at = models.DateTimeField(auto_now_add=True)

7. LIMITATIONS

7.1 Cloud Free-Tier Spin-Down Boundary: On Render's free deployment tier, backend instances spin down after 15 minutes of inactivity, requiring ~30-50s to wake up on the initial request.

7.2 Ephemeral File Storage: While PostgreSQL data on Neon is permanent, Render free containers use ephemeral disks. Files uploaded locally reset upon container redeployments unless hosted on cloud object storage (e.g. AWS S3).

7.3 Manual Committee Review: Review relies on human faculty validation rather than automated OCR comparisons against university ERP ledgers.
