1. INTRODUCTION

Academic credential management, verification, and placement screening across higher educational institutions continue to face severe inefficiencies due to legacy paper-bound workflows and unauthenticated digital assets. Higher education institutions handle tens of thousands of degrees, marksheets, certificates, and internship letters annually. When students apply for placement recruitment or higher education abroad, background screening agencies and corporate HR departments spend weeks attempting to verify the validity of photocopies and unverified PDFs. EduVault addresses this systemic vulnerability by serving as a secure, decentralized digital locker and cryptographic verification platform.

This chapter examines the existing institutional procedures and their inherent vulnerabilities, details the architecture of the proposed EduVault platform, defines the system scope, specifies the hardware and software operating environment, and provides a technical justification for every chosen technology in the stack.

1.1 EXISTING SYSTEM, PROPOSED SYSTEM AND NEED AND OBJECTIVE OF SYSTEM

1.1.1 Existing System

The contemporary academic ecosystem operates across fragmented administrative silos. Existing workflows fall into four primary mechanisms:

(a) Physical Photocopies and Attested Transcripts. Students obtain paper marksheets, physically visit institutional offices for authorized rubber stamps and signatures, and submit paper bundles during campus drives. Paper certificates degrade, are easily lost or damaged, and incur ongoing storage and courier costs.

(b) Unauthenticated Scans and Vulnerability to Alteration. Students frequently share electronic PDF scans via email. However, non-cryptographic PDF documents can be altered using modern editing tools to forge marks, alter names, or generate counterfeit graduation certificates. Recruiters cannot determine authenticity from visual inspection alone.

(c) Disconnected Placement Operations. Campus placement cells (Training & Placement Offices) spend days manually compiling, verifying, and formatting candidate spreadsheets (CGPA, active backlogs, achievements, and project links). These spreadsheets are static and prone to student self-reporting errors.

(d) Static and Inaccessible Alumni Directories. Institutions maintain stagnant Excel databases of graduated alumni. Students looking for career mentorship or job referrals have no real-time platform to discover alumni by employer, role, or mentorship availability.

1.1.2 Proposed System

EduVault is a role-governed, cloud-native Digital Locker and Academic Credential Verification Platform. The system decouples presentation, business logic, and database persistence into an asynchronous client-server architecture supporting four distinct institutional roles:

  1. Student Vault: Provides students with a digital locker to upload marksheets, certificates, internships, and project portfolios. Features an instant cryptographic Interview Key that compiles approved credentials into a verified QR code for mobile scanning.
  2. Academic Verification Committee: A dedicated institutional validation queue where faculty reviewers inspect original uploads via an in-app viewer, approve genuine records, or reject invalid submissions with actionable feedback.
  3. Campus Placement & Corporate Relations Portal: A recruiter-facing portal offering real-time candidate search, department filtering, and CGPA thresholds (e.g. ≥ 9.0, ≥ 8.0) directly linked to verified dossiers.
  4. Dynamic Alumni Network: An interactive directory where graduated alumni can update their current employer, designation, location, and toggle a public mentorship availability badge.
  5. Public Verification Gateway: Open, secure endpoints allowing corporate interviewers to scan QR codes or open unique links (/student/:id or /verify/:verification_id) to view authenticated dossiers on mobile or desktop without login credentials.

1.2 SCOPE OF WORK

1.2.1 Functional Scope

User Authentication & Profile Lifecycle: Registration and login with JWT access and refresh tokens. Dedicated profile management for students (PRN, CGPA, Batch, Skills, Bio) and alumni (Company, Designation, Location, Mentorship toggle).

Document Vault Management: Secure uploading, category assignment (Certificate, Marksheet, Internship, Project, Achievement, Other), status tracking (Pending, Verified, Rejected), and document deletion safeguards for pending items.

Committee Verification Pipeline: Filterable review queue, in-app modal document previewer supporting PDFs and image formats, single-click approval, and granular rejection feedback dispatch.

Campus Placement Talent Engine: Aggregate metrics (Total Candidates, Drive Eligible, Avg CGPA), multi-parameter search, CGPA threshold pills, and candidate profile drawers.

Dynamic Alumni Directory: Searchable alumni cards with company badges, designation tags, and mentorship contact points.

Public Verification Gateway: Open, unauthenticated dossier view (/student/:id) and direct certificate verification page (/verify/:id) for corporate interviewers.

1.2.2 Technical Scope

Backend Architecture: Python 3.11 with Django 6.0 and Django REST Framework, utilizing Gunicorn as the production WSGI application server.

Database Persistence: PostgreSQL 16 hosted on Neon Serverless Cloud, managed via Django ORM with full ACID compliance and foreign key cascade constraints.

Frontend Client: React 18 SPA built with Vite bundler, utilizing Tailwind CSS for utility-first styling and Lucide React icons.

Cryptographic Generation: UUIDv4 tokens generated per document, compiled into client-side rendered QR codes using qrcode.react and QRServer API.

Cloud Infrastructure: Vercel for frontend SPA edge delivery; Render for backend container hosting; Neon for serverless PostgreSQL database.

1.2.3 Out of Scope and Boundaries

The following areas are explicitly excluded from the current version of the project:

1.4 DESCRIPTION OF TECHNOLOGY USED

1.4.1 Python 3.11 Runtime Environment

Python 3.11 serves as the primary backend programming language for EduVault. It introduces substantial performance enhancements over prior versions through the Specialized Adaptive Interpreter (PEP 659), delivering up to 25% faster execution. Python provides clean, readable syntax, robust type-hinting, native datetime handling, and an extensive ecosystem of enterprise web packages.

1.4.2 Django 6.0 and Gunicorn WSGI Server

Django 6.0 is a battle-tested, high-level Python web framework designed on the Model-View-Controller (MVC) architectural pattern. Django provides an integrated Object-Relational Mapper (ORM) that prevents SQL injection attacks through parameterized queries. It automatically manages database schema migrations, enforces session security, and includes cross-site scripting (XSS) filters. In production on Render, Gunicorn (Green Unicorn) acts as a pre-fork worker WSGI server capable of handling multiple concurrent requests efficiently.

1.4.3 Django REST Framework (DRF) & SimpleJWT

Django REST Framework empowers the backend with flexible, serializable RESTful API endpoints. DRF provides model serializers that translate complex ORM querysets into clean JSON payloads and validate incoming multipart form data. Authentication is handled using rest_framework_simplejwt, which issues cryptographically signed JSON Web Tokens (RFC 7519). The architecture separates short-lived access tokens (15-minute lifespan) from long-lived refresh tokens (7-day lifespan), ensuring secure, stateless session management.

1.4.4 React 18 & Vite Tooling

The user interface is built as a Single-Page Application (SPA) using React 18 and Vite. React's virtual DOM and reactive hooks (useState, useEffect, useMemo, useRef) enable instant UI updates without whole-page refreshes. Vite replaces legacy Webpack bundlers, utilizing native browser ES modules (ESM) to provide sub-second hot module replacement (HMR) during development and lightning-fast Rollup builds for production deployment.

1.4.5 Tailwind CSS Utility-First Framework

Tailwind CSS is an industry-leading utility-first CSS framework. Rather than writing arbitrary custom CSS classes, interface components compose utility classes directly in JSX. Tailwind's modern color palette, spacing scale, and responsive prefixes (sm:, md:, lg:, xl:) ensure consistent design across desktop monitors, laptops, tablets, and smartphones.

1.4.6 PostgreSQL 16 & Neon Serverless Persistence

PostgreSQL 16 is an advanced open-source Object-Relational Database Management System (RDBMS). It provides full ACID (Atomicity, Consistency, Isolation, Durability) transactional compliance, ensuring that operations such as user registration and document status transitions never leave the database in an inconsistent state. EduVault uses Neon Serverless PostgreSQL, an autoscaling cloud database service with zero maintenance overhead, automated failover, and high concurrent query throughput.

1.4.7 QRCode.react & Cryptographic Verification Engine

To enable frictionless physical-to-digital credential inspection during in-person interviews, EduVault incorporates client-side QR generation. Each student profile and verified credential generates an immutable public URL encoded into a high-density matrix barcode. Using qrcode.react and the QRServer API, the system renders vector SVG and PNG barcodes on screen. An interviewer simply points any smartphone camera at the student's screen to load the official verified dossier on their mobile browser.

1.4.8 WhiteNoise Static Serving & Cloud Deployment

In standard Django deployments, serving static assets (CSS, JS, images) requires configuring a separate web server like Nginx. EduVault utilizes WhiteNoise, a lightweight Python middleware that integrates directly into the WSGI pipeline. WhiteNoise manages static asset serving with gzip and Brotli compression, generating unique content hashes for immutable caching headers. The application is deployed across global edge networks via Vercel (frontend) and Render (backend).

2. PROPOSED SYSTEM

EduVault is designed as a decoupled, service-oriented platform organized into four tiers. Each tier carries a distinct responsibility and communicates with its peers exclusively through authenticated REST contracts:

  • Decoupling: The React client knows only the REST contract and receives JSON responses. The Django backend operates independently of client view presentation. Either tier can be refactored or updated without breaking the other.
  • Asynchronous Execution: Document uploading, status verification, and search filtering execute asynchronously via REST APIs, keeping the client interface responsive.
  • Strict Role Isolation: Role guards evaluate permissions on every endpoint. Students cannot inspect committee review queues; committee members cannot manipulate placement thresholds.

5.4 DEFECTS FOUND AND RESOLVED

5.4.1 Defect 1: Production Media File 404 Resolution via re_path & serve

Table 5.4: Defect record for DEF-01.
Field Detail
IDDEF-01
Componentconfig/urls.py, Django Media Routing
SeverityHigh. Uploaded student certificates returned 404 Not Found on cloud deployment.
Detected InProduction integration testing on Render and Vercel.
StatusResolved.

Symptom: When students uploaded certificates and clicked "View File", the browser returned "404: Not Found - The requested resource was not found on this server."

Root Cause: By default, Django serves media files only when settings.DEBUG = True using urlpatterns += static(settings.MEDIA_URL). On the production Render deployment, DEBUG was set to False, causing Django to disable the media routes entirely.

Resolution: Updated config/urls.py to explicitly route media requests through django.views.static.serve using re_path across all environments:

from django.urls import re_path
from django.views.static import serve
from django.conf import settings

# Explicitly enable media file serving in production
urlpatterns += [
    re_path(r"^media/(?P.*)$", serve, {"document_root": settings.MEDIA_ROOT}),
]

from django.db import models

class UserManager(BaseUserManager):
    def create_user(self, email, password=None, **extra_fields):
        if not email:
            raise ValueError("The Email field must be set")
        email = self.normalize_email(email)
        user = self.model(email=email, **extra_fields)
        user.set_password(password)
        user.save(using=self._db)
        return user

6.2 DOCUMENT VALIDATION & ENCRYPTION MODEL (documents/models.py)

import uuid
from django.db import models
from django.conf import settings
from django.core.exceptions import ValidationError

def validate_document_file(value):
    max_size = 5 * 1024 * 1024  # 5 MB
    if value.size > max_size:
        raise ValidationError("File size must not exceed 5 MB.")
    allowed_extensions = [".pdf", ".jpg", ".jpeg", ".png"]
    if not any(value.name.lower().endswith(ext) for ext in allowed_extensions):
        raise ValidationError("Only PDF, JPG, JPEG, and PNG files are allowed.")

class Document(models.Model):
    user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name="documents")
    verification_id = models.UUIDField(default=uuid.uuid4, unique=True, editable=False)
    title = models.CharField(max_length=200)
    category = models.CharField(max_length=20)
    file = models.FileField(upload_to="documents/", validators=[validate_document_file])
    status = models.CharField(max_length=20, default="PENDING")
    rejection_reason = models.TextField(blank=True, null=True)
    verified_at = models.DateTimeField(blank=True, null=True)

6.3 COMMITTEE VERIFICATION & REJECTION VIEW (documents/views.py)

from django.utils import timezone
from rest_framework import status
from rest_framework.response import Response
from rest_framework.views import APIView
from .models import Document
from .permissions import IsCommittee

class VerifyDocumentView(APIView):
    permission_classes = [IsCommittee]

    def post(self, request, pk):
        try:
            document = Document.objects.get(pk=pk)
        except Document.DoesNotExist:
            return Response({"error": "Document not found."}, status=status.HTTP_404_NOT_FOUND)

        document.status = "VERIFIED"
        document.verified_at = timezone.now()
        document.rejection_reason = None
        document.save()
        return Response({"message": "Document verified successfully.", "verified_at": document.verified_at}, status=status.HTTP_200_OK)

6.4 DYNAMIC API MEDIA RESOLVER (src/api/apiClient.js)

export const API_BASE_URL =
  typeof import.meta !== "undefined" && import.meta.env?.VITE_API_URL
    ? import.meta.env.VITE_API_URL.replace(/\/$/, "")
    : "";

/**
 * Returns full absolute URL for uploaded media files.
 * In production on Vercel, ensures relative /media paths target the Render backend.
 */
export const getMediaUrl = (url) => {
  if (!url) return "";
  if (url.startsWith("http://") || url.startsWith("https://")) {
    return url;
  }
  const cleanPath = url.startsWith("/") ? url : `/${url}`;
  return `${API_BASE_URL}${cleanPath}`;
};

Explanation of Implementation Mechanics

Role-Based Permission Enforcement: Permissions are checked at the REST API view level using custom DRF permission classes (IsCommittee, IsPlacementOrCommittee) which inspect the authenticated JWT claims. If an unauthorized role attempts access, Django immediately terminates the request with HTTP 403 Forbidden without database query overhead.

Stateless JWT Token Lifecycle: User credentials are exchanged for HMAC-SHA256 signed tokens. The client stores tokens in browser memory and attaches the bearer token to the HTTP Authorization header for every subsequent API request.

7. LIMITATIONS

7.1 Render Free-Tier Spin-Down (Cold Starts)

Table 7.1: Operational limitation on free cloud hosting.
Aspect Detail
Cause Render's free tier spins down idle web service containers after 15 minutes of inactivity to preserve compute resources.
Symptom The initial HTTP request sent after dormancy requires 30 to 50 seconds while the container initializes and launches Gunicorn.
Mitigation In a commercial production environment, upgrading to Render Starter ($7/mo) or AWS Elastic Beanstalk provides 100% active uptime.

7.2 Ephemeral Container Storage vs. Persistent RDBMS

On Render free instances, the local container filesystem is ephemeral: while the PostgreSQL database on Neon is permanent, locally stored media files in media/ reset if the container restarts. In enterprise production, media storage must be delegated to dedicated object stores (e.g. Amazon S3 or Cloudinary).

7.3 Manual Committee Review Dependency

Credential verification currently relies on authorized human faculty inspection. Automated AI-based OCR cross-referencing against university records is not yet incorporated.

7.4 Operational and Evaluation Limits

The system requires an active internet connection to execute authentication and verification. An offline Progressive Web App (PWA) cache mode is not currently enabled.
